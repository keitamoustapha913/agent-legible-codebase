# Isolated-verifier mode

Use `--mode isolated-verifier` when a restricted Codex shell cannot run the application tests and an approved, offline QEMU verifier image is available. The default edit mode needs no VM or runtime probe. Advanced sandbox qualification remains available separately. The isolated mode has its own guest, agent-sandbox, and frozen-baseline readiness gates.

## What runs where

- **Agent:** Codex stays in a named workspace-write sandbox with networking disabled and its approval policy set to never. Only the checkout is writable. The shell and integrations are disabled. The agent has a read-only navigation service and uses the native sandboxed patch tool. A local sandbox probe checks the write boundary, hidden verifier inputs and disabled IP sockets. A run with observed shell or unknown tool actions is invalid.
- **Controller:** The development host runs the skill, Git, Codex, filesystem image creation, and QEMU. It never runs setup, success, or regression commands from the manifest in this mode. It packages selected regular Git worktree files, rejects symlinks, hardlinks and special files, and pins candidate and verifier inputs by SHA-256. Git metadata and ignored dependency and build output are omitted. Setup reproduces dependencies inside the VM.
- **Verifier:** Every job boots a fresh Linux QEMU guest with a checksum-pinned kernel and initramfs. QEMU has no NIC, shared filesystem, inherited developer environment, interactive monitor, or persistent guest disk. Its only job device is a read-only block image. The guest runs manifest commands as an unprivileged UID with a small environment and wall deadlines. Privileged guest code protects the input disk and verdict stream, checks isolation and local asyncio, and compares the candidate checksum. The verifier verdict is bound to the request nonce, task, revision, manifest checksum, candidate checksum, VM profile and QEMU fingerprint.
- **Results:** The report keeps VM infrastructure and independent correctness checks separate from agent actions, provider usage and architecture evidence. A stale or missing verdict, changed protected path, failed boot, invalid artifact, or timed-out check invalidates readiness. No model session runs after a failed readiness gate. This is a distinct experiment mode with different agent feedback. Compare its paired runs only within this mode.

## Qualify the VM before using it

Prepare a reviewed, credential-free x86-64 Linux initramfs and an up-to-date QEMU build. The VM is intentionally provisioned outside the benchmark runner. Use a kernel with virtio PCI, virtio block and the ext2 filesystem enabled or load the matching modules from the initramfs. The initramfs needs `/usr/bin/python3` with the standard library, `/usr/bin/env`, `/usr/bin/setpriv`, mount and power-off utilities, and the offline project dependencies and runtimes. Use [the init script](../scripts/verifier_vm_init.sh) as the boot entry point and load any necessary drivers first. The script mounts `/dev/vda` read-only under a root-only parent and delegates the job to the sealed worker in the input image.

For Sales, the image must include the frozen task's Python 3.14.6 and uv-compatible offline packages. The guest provides only `/opt/alc-python` as its Python installation directory and `/var/cache/alc-uv` as its cache directory. Give the test UID appropriate access to both within the guest. The [Sales VM profile example](../examples/sales.verifier-vm.example.json) includes the original independent verifier digest and shields the regression test and pytest configuration. Fill in the reviewed boot assets and their real digests, save the profile outside both the target repo and the output directory, and keep every frozen task command intact. A profile can provide guest-only writable scratch directories needed beneath protected ancestors.

Run the frozen Sales plan from the skill directory with `--mode isolated-verifier --verifier-vm-profile /path/to/reviewed.json --trials 1 --readiness-only --approve-manifest` plus the existing repo, manifest, oracle contract, revisions, model and fresh output options. Omit `--sandbox-smoke` because this mode does not run tests inside the Codex sandbox. The readiness command requires approval for the trusted manifest checks and consumes zero model sessions. It boots one probe VM and one VM per baseline task/revision. After all checks pass, an explicitly approved run without `--readiness-only` would schedule four model sessions and an independent candidate VM for each. No model session is needed for VM startup, baseline checks, or post-edit verification.

Use reviewed boot and QEMU artifacts. The runner checks digests and isolation settings, and a successful probe depends on the integrity of those trusted components. The guest isolation boundary limits the effects of untrusted application code and cannot make a weak behavior test independent or provide a proof against hypervisor defects. If the live agent does not expose the native patch tool for the selected model, that tooling profile remains unqualified.
